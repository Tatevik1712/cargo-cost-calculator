# DECISIONS.md — Журнал архитектурных решений (ADR)

Каждая запись фиксирует: контекст, принятое решение, альтернативы и
последствия. Новые решения добавляются в конец файла, старые не удаляются.

---

## ADR-001 — Прайсы РТТК/БРЛ хранятся в Excel/CSV-файлах, а не в БД

**Дата:** до начала данной сессии доработки.

**Контекст:** Перевозчики РТТК и БРЛ предоставляют тарифы в виде готовых
Excel-таблиц. Объём данных небольшой, обновления — редкие и вручную
(через `/api/admin/upload`).

**Решение:** Читать цены напрямую из xlsx/xls/csv в `backend/data/` через
`pandas`, без промежуточной БД.

**Альтернативы:** Импорт в SQL/NoSQL БД с ETL-процессом при загрузке файла.

**Последствия:** Проще для старта и для непрограммиста-администратора
(просто заменить файл), но парсинг завязан на конкретный визуальный формат
таблицы (см. `ARCHITECTURE.md`, раздел «Модель данных прайсов») — при
масштабировании до БД стоит вернуться.

## ADR-002 — Список городов вычисляется динамически из прайсов

**Дата:** 2026-08-05 (в рамках текущей сессии).

**Контекст:** Изначально список городов для выпадающих списков «Откуда»/
«Куда» был захардкожен во фронтенде (`getAllCities()` в `calc.ts`) — 10
городов. Требование: список должен браться из реальных данных перевозчиков
(РТТК + БРЛ), без дублей.

**Решение:** Backend-эндпоинт `GET /api/v1/cities` собирает города из
заголовков маршрутов обоих прайс-файлов (`LocalCalculatorService.get_available_cities()`),
складывает в `set()` для дедупликации, нормализует варианты написания
(например, «Питербург» → «Санкт-Петербург») и возвращает отсортированный
список. Фронтенд запрашивает этот список при монтировании компонента.

**Альтернативы:** Держать список городов синхронизированным вручную во
фронтенде при каждом обновлении прайса — отклонено как источник рассинхрона.

**Последствия:** Список городов всегда актуален относительно загруженных
прайсов. Цена — усложнение парсера (эвристический разбор заголовков
маршрутов регулярными выражениями).

## ADR-003 — Тестирование через двойной ngrok-туннель

**Дата:** до начала данной сессии, зафиксировано в этой сессии.

**Контекст:** Нужно давать доступ тестировщикам без полноценного деплоя.

**Решение:** Запускать backend и frontend локально, поднимать по отдельному
ngrok-туннелю на каждый (`ngrok http 8000` и `ngrok http 8080`).

**Альтернативы:** Полноценный деплой на облачный хостинг — отложено до
готовности продукта.

**Последствия:** Бесплатный ngrok показывает интерстициальную HTML-страницу
предупреждения при первом обращении браузера — без заголовка
`ngrok-skip-browser-warning: true` в запросах фронта это выглядит как
CORS-ошибка (см. ADR-004 и `CHANGELOG.md`). URL туннелей меняются при каждом
перезапуске — `VITE_API_BASE_URL` нужно обновлять вручную.

## ADR-004 — Явная обработка ошибок сети на фронтенде, без тихих fallback-ов

**Дата:** 2026-08-05.

**Контекст:** Изначальная реализация `getCitiesFromBackend()` перехватывала
любую ошибку сети (`catch`) и молча возвращала статический список городов.
Это маскировало реальную проблему (сломанный CORS через ngrok, а затем —
отсутствующий `.catch()` в вызывающем компоненте, из-за чего даже успешный
рабочий бэкенд не подхватывался, если промис отклонялся по любой причине)
и не давало понять пользователю/разработчику, что бэкенд недоступен.

**Решение:**
- Убрать статический список городов (`getAllCities()`) из кодовой базы
  полностью.
- `getCitiesFromBackend()` бросает ошибку вместо тихого fallback.
- В `CargoCalculator.tsx` добавлены явные состояния `citiesLoading` /
  `citiesError`, отображаемые в UI, и выпадающие списки блокируются
  (`disabled`), пока города не загружены.

**Альтернативы:** Оставить fallback, но логировать ошибку в консоль —
отклонено, так как ошибка легко пропускается при тестировании через сторонних
людей, у которых нет доступа к консоли браузера.

**Последствия:** Любая проблема с бэкендом теперь сразу видна в интерфейсе.
Обратная сторона — форма непригодна для использования, пока бэкенд
недоступен (это осознанный компромисс: лучше явный сбой, чем скрытые
неактуальные данные).

## ADR-005 — Тип доставки «Экспресс» удалён

**Дата:** 2026-08-05.

**Контекст:** В форме был переключатель типа перевозки «Авто» / «Экспресс»,
но реальной бизнес-логики и тарифов для «Экспресс» не было ни на бэкенде,
ни у перевозчиков.

**Решение:** Убрать переключатель и связанный стейт из
`CargoCalculator.tsx`, тип перевозки зафиксирован как константа `"auto"`.

**Альтернативы:** Оставить как задел на будущее — отклонено, так как
нереализованная опция в UI вводит пользователя в заблуждение.

**Последствия:** Если понадобится вернуть «Экспресс», нужно будет
реализовать реальную бизнес-логику (тарифы, сроки) и на бэкенде, и на
фронте, а не просто вернуть UI-переключатель.
